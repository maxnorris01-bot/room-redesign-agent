# Session: stage D1.2, no invite codes; anonymous visitors with address-based limits (2026-10-31)

Nothing here has run on the live deployment or on real PostgreSQL; no git, gh, fly or docker command was run. Decision by the owner (2026-10-31); ADR 0014 records it.

## What changed and why
Invite codes were more trouble than they are worth for a portfolio demo. Every visitor now gets an automatic anonymous session; limits protect the spend.
- **Visits:** `POST /auth/start` (no body; origin secret, Host and Origin checks as before) makes a visitor and a login session and sets the `shop_login` cookie (128 random bits, only the SHA-256 stored, HttpOnly, SameSite=Lax, Secure per `APP_PUBLIC_URL`, `Path` = the prefix, 30 days, extended when used). Protected routes without it answer `401 session_required` (renamed from `login_required`). `GET /auth/session` has no label now and its `usage` is `{ip_day, session, resets_at}`. Removed: `/auth/login`, invites, revoke, the code login limiter, the `invite` admin commands, `APP_CAP_INVITE_DAY_USD`.
- **Limits:** $0.50 per shop session, $1.00 per visitor address per UTC day (`ip_day`), $2.00 per UTC day for everyone (was $3.00), 8 searches and 25 Shop Agains per session; 20 visitors per address and 200 in all per day, 10 starts per address per minute (429 `rate_limited` with `Retry-After`). All by environment (`thresholds.py` holds the defaults and the reasons). The daily spend follows the address stored when the visitor was created, so clearing cookies resets nothing.
- **Addresses:** only from the trusted `x-forwarded-for`; stored as HMAC-SHA256 under a key derived from `APP_ORIGIN_SECRET` (rotating the secret resets the address counters; said in `docs/deploy.md`).
- **Retention:** visitors, logins and shop sessions unused 30 days, and usage rows older than 40 days, are deleted at start, lazily from a request at most every 6 hours (no timer thread) and by `python -m app.shop.admin purge`. A purge failure is logged and never fails a request.
- **Admin:** `migrate`, `caps show` (adds today's global spend and visitors created today), `purge`. It prints no secret and no address.
- **Bot check hook:** `auth.bot_check_allowed` is called by `/auth/start`, allows everything and makes no third-party call (todo: Turnstile).
- **Migration 2** (idempotent, one transaction): deletes the invite-owned data (test data only: invite-day counters, the usage rows and shop sessions an invite owned, every login session), drops `invites`, renames `invite_id` to `visitor_id` on `shop_sessions` and `login_sessions` (`ALTER TABLE ... RENAME COLUMN`, valid on SQLite 3.25+ and PostgreSQL), adds `visitors` and indexes. Today's global counter is kept. On a version-1 database with sample rows the test shows: invites gone, the invite-owned session and all logins gone, the unowned session and global counter kept, versions `[1, 2]`, and the store works afterwards; running `migrate` twice changes nothing. The service still migrates at start.
- Docs: `docs/api-contract.md` (and its test), `docs/deploy.md` (no invite steps, new settings table, first-use checklist, spend check, secret rotation note), ADR 0014 (ADR 0013 marked amended), SPEC, todo, working notes. `scripts/deploy_smoke.py` now does a visit start, search, `cap_reached`, the start limit, the kill switch and healthz.

## What only real PostgreSQL can prove
Migration 2 on a real version-1 database (rename column, drop table, the `ON CONFLICT ... DO UPDATE SET searches = usage.searches + 1` form, the JOINs); concurrent starts near the daily visitor cap (the check and increment share one transaction, but PostgreSQL's default isolation would let two commit past the cap by one); the retention deletes on real data; behaviour after Neon's idle suspend.

## Flag for review
- The per-address cap is tied to the address recorded when a visitor was created: a visitor whose address changes keeps spending against the old one, and a new address gets a fresh $1.00 until the global cap. An office or phone network shares one $1.00.
- `x-forwarded-for` from Vercel is assumed to be the client address (unverified); if it is wrong, every visitor shares one address and the $1.00 per-address cap becomes a second global cap.
- The limiter for starts per minute is in memory (one machine).
