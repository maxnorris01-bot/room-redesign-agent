# Working notes and decisions log - Room Redesign Agent

This is a different kind of record from `docs/sessions/*.md`. Session docs narrate what changed in
one sitting and are written for someone with zero context picking up the diff. This file is the
opposite shape: short, durable entries - a decision plus *why*, or an open item worth remembering -
meant to be skimmed months later when the reasoning behind something has otherwise been forgotten.
Append to it whenever a real decision gets made, not just at the end of a session. If something is
already fully documented elsewhere (a technical fix in a session doc, a known failure in the
README, a design tradeoff in an ADR), point to it here rather than duplicating it.

**2026-10-24 - Shop Mode stage 2c: the model describes, code decides (ADR 0012 amended).** Fed by live use on the owner's real ratings: two loved round and two loved rectangular West Elm tables ($699 to $899) plus eight liked across sellers gave the chip "round drum", the dislike "rectangular with drawers" (a loved item has it) and learned values written into the request chips. Cause: the model decided what counted as a preference and over-read mixed likes, and a mostly round batch made "likes round" look true (exposure feedback). Decisions, each with its reason: (1) the model only tags each rated item along fixed dimensions (prompt v3); code decides from ALL ratings every time, so the same ratings give the same profile in any order and nothing drifts; (2) a value is preferred only if it holds 70% of the like mass, has 2 supporting items and beats its share of what was shown by 1.3 (the exposure baseline comes from a title-keyword lexicon, no model call), and two or more values at 30% each are "open": a neutral chip with no pressure, which is the honest reading of liking both shapes; (3) a dislike needs 2 disliked items sharing a value no loved or liked item has, and one dislike only excludes that item; (4) price is "mixed" when loved prices are upper but liked prices span two thirds of the range, so a premium loved set stops capping the search; (5) request chips show only what the parser read, learned values live in the preference chips, and the adjusted query is stored apart (`used_query`), because writing learned values back is what kept pushing round; (6) one search phrasing per value of an open dimension (each carrying the converged words), never one value in every phrasing, with the typed phrasing and the seller phrasing kept, and the dropped phrasings recorded when the 4-call cap bites; (7) a 60% single-value cap on guarded dimensions (open ones, plus shape and material while not converged) and a 50% seller cap (80% pinned) are enforced on the final 24 in code, because the ranker was told but a prompt is not a guarantee; if a pool cannot meet a guard the remainder is returned with a message; (8) the seller chip is the pin control (click to pin), stored in the session; (9) the Saved panel is a wrapping grid. All thresholds are in `src/app/shop/thresholds.py` (table in ADR 0012) for the stage 3 eval to tune. Judgement calls to check live: dark and brass metal are one frame-colour value in the lexicon; style and size have no reliable baseline. Not verified live: model tags on real photos, the lexicon against real titles, the thresholds on real ratings. Mock-verified only; see `docs/sessions/2026-10-24-shop-mode-stage-2c.md`.

**2026-10-24 - Shop Mode stage 2b: learn from the items, a wider pool, lookups only on Open (ADR 0012 amended).** Fed by live use of stage 2: results did not feel aligned with what the owner loved unless a comment said so, the chips restated the request, a parser-guessed "industrial" was treated as a settled like, and Shop Again re-ran nearly the same search. Decisions, each with its reason: (1) the preference call (prompt v2) now sees each rated item and up to 16 thumbnails (6 loved, 6 liked, 4 disliked) through the existing guarded fetcher, and returns inferred attributes with evidence ids; the model proposes, code decides: two items of evidence unless a comment backs it, a net weight (loved 3, liked 1, minus disliked matches), visible quality cues only, seller affinity (two loved or liked, no dislike) and a price band (top or bottom third of the shown prices) computed from the ratings and not from the model, because those are the signals the owner's two West Elm tables actually shared and a model's say-so on them is not evidence; (2) a price band is a preference signal only and never changes the typed cap; (3) a style term the parser produced but the request does not contain is a guess: marked, not a like, dropped when a loved or liked item contradicts it (the model reports it, code checks the evidence and the titles) or when deleted; (4) the stated likes are only the shopper's own words, an inferred phrase equal to a stated one is shown once as the shopper's; (5) up to three phrasings (adjusted query, attributes, seller name) inside a 4-call cap, each phrasing's first page always, extra pages only while the pool is under 60, and a repeated phrasing continues after the pages the session already fetched, so the same page is never bought twice; (6) the ranker (prompt v3, 80 candidates) is told how reliable each part of the profile is and that guesses are not likes; the seller cap is 8 for an affinity seller; (7) lookups happen only on Open, so loving costs nothing; (8) the alignment measure (matches of inferred likes with no dislike) is a diagnostic for stage 3, not a gate; (9) the mock gained a premium invented seller in the fixtures, a mock search engine that surfaces it for specific queries, and the coffee-table sample now carries a parser guess ("industrial"), so every new path can be exercised offline. Untuned guesses: the 2-item evidence rule's exceptions, thirds for the price band, 16 images, pool target 60 and cap 80, seller cap 8, 4 Serper calls. Not verified live: Serper pages 3 and 4, how the model reads real photos, whether the extra phrasings add fresh results. Mock-verified only; see `docs/sessions/2026-10-24-shop-mode-stage-2b.md`.

**2026-10-24 - Shop Mode stage 2: Shop Again, preference chips, Saved, cost in credits (ADR 0012 amended).** Built from the live findings of stage 1 (thumbnails load, a lookup is one search, a Serper shopping call is 2 credits and the footer under-counted, a search takes about 11 s with no loading cue). Decisions, each with its reason: (1) the profile is the complete list returned by one small-model call, not a delta, with the rules the model cannot be trusted with enforced in code (deleted entries never return, category and price floor never change, `price_max` may only fall by at most 20% of the typed cap and only with a stated reason), so the page can show it as chips the visitor deletes; (2) Shop Again always adjusts the last typed query, never an earlier Shop Again's, so adjustments do not stack and a deleted chip really disappears; (3) exclusion is by result id and by the same title and seller, because the same listing can come back under another product id; (4) a seller is ranked last, not excluded, only with 2 or more dislikes and no love or like from it; (5) paging goes to 3 pages and stops at an empty page, and a short result says "Only N new results found" instead of padding with seen ones; (6) Saved is derived from ratings and stored results (nothing extra stored), so a re-rate or a clear removes an item with no extra bookkeeping; (7) the preference row is shown whenever there are results, with a hint, so the first Shop Again does not shift the grid; (8) Serper cost is calls x credits x USD per credit (2 and 0.001, the owner's figure, env-overridable); the room pipeline keeps its own per-query figure; (9) a rating's timestamp now has millisecond resolution and the page uses the same format, because Saved is ordered by it; (10) the 2D-plan reason in ADR 0012 is now the owner's: judged useless to visitors, the photo is the output. Untuned guesses: 10 Shop Agains per session, 3 pages, the 20% cut, 12 phrases, 8 examples to the ranker. Not verified live: Serper `page` 3, real comment interpretation, whether unseen holds on small result sets. Mock-verified only; see `docs/sessions/2026-10-24-shop-mode-stage-2.md`.

**2026-10-24 - Two modes: Shop Mode first, Redesign Mode later; the 2D plan is dropped (ADR 0012, proposed).** Owner decision: the product is now a curated product search with no room photo (Shop Mode: type a request, browse a grid, rate each result love, like or dislike with an optional comment) and, after it works, Redesign Mode (room photo, stripping furniture, photo-real render). The 2D plan leaves the product; its code stays only in the developer run report. Stage 1 built: a small-model parse of the request into a typed query, Serper search, hard filters for price and category (code), dedupe, a 4-per-seller cap, an id-only ranker for the soft preferences (style, materials, must-haves, avoid), the top 24, and a local page on 127.0.0.1. Decisions made while building, each with its reason: (1) lookups are lazy, only on Open or Love, at most 12 per session, never twice (a lookup is about $0.025 and would be about $0.60 for a full page), and a failed lookup is cached as a marked Google-link fallback so a click never re-spends; (2) the seller cap is applied after ranking so each seller's best results survive, and results the ranker omits follow in search order so the grid still fills; (3) page 2 is fetched only when fewer than 24 results could be shown after the filters and the seller cap; (4) the category check is title keyword matching against `categories.py` (an unknown category like "curtains" is never filtered); (5) a rating needs no comment and a comment needs no rating, and clearing both removes the record; (6) the session id lives in the browser's local storage, and an unknown id gives an empty page rather than an error; (7) the server checks Host, Origin and content type, caps bodies at 8 KB and sends a strict CSP, because any web page open in the visitor's browser could otherwise call a local server that spends money; (8) the prompts live in `prompts/` with the others (not `src/prompts/`). Untuned guesses: 24 results, 4 per seller, 12 lookups, 50 searches per session, the accessory word list. Not verified live: Serper's `page` parameter, real page sizes, ranker quality. Terms of showing Google Shopping results and thumbnails publicly are unreviewed (ADR 0012). Mock-verified only; see `docs/adr/0012-two-modes-shop-first.md`, `docs/sessions/2026-10-24-shop-mode-stage-1.md`.

**2026-10-22 - Pick quality: sizes from titles and slugs, matching sets, seller variety, an image style check (ADR 0009 and 0010, proposed).** Fed by the latest live freeplay run. Sizes: fit was "unknown" on every pick although sizes sit in the data (`sanders-85-5-sofa`, `leif-54-media-unit`, `79"W` in titles); trust order is lookup features, then titles (store title first), then the URL slug; per-category plausible ranges discard mis-parses (and a real size on the wrong product); each candidate has `size_source` and `size_confidence` (slug = low, and the fit message says "approximate"); partial sizes get the longest-side rule only; a replacement more than 25% longer or shorter than the old piece gets a note. Sets: optional `matches_id` on perception furniture (additive, so `schema_version` stays 1), perception prompt v3 default, a note-text fallback marked inferred; a kept set member of a replaced item is a warning, `--replace-matching` replaces it, and the proposal gets the set as data. Families (storage, occasional tables, chairs, extra seating, lighting, bedroom storage) allow one slot each unless a replacement was explicitly requested, with the next category refilling; the item-count message says what happened; this lowers the per-room maximum (living 8, bedroom 9, office 7, dining 8), a deliberate trade against duplicates like media unit plus console table. Variety: freeplay rank pools cap any one seller at 3 and rank prompt v5 asks for variety; concentration is reported, not enforced across slots (that would need a barrier before lookups). Image check: thumbnail of each slot's top-ranked finalist fetched in parallel with its lookup (https only, public hosts, 3 s, 1 MB, image types only, no query in logs), style prompt v2 (default; v1 text-only stays) sees the room photo, thumbnails and the kept items' colours, a strong clash or poor match is a warning and can trigger the one revision. Mock mode serves a generated image; no test uses the network. Untuned guesses: size ranges, 25% replacement tolerance, seller cap 3, 10 thumbnails, 256 px, family groupings. Mock-verified only. **2026-10-21 - Retrieval default is now two-stage shopping data (ADR 0005, proposed).** Why: web-search retrieval had the model read pages and report prices and URLs itself (listing pages, one invented price). **2026-10-18 - Spike skeleton decisions (Claude Code session 1).** Details in `docs/sessions/2026-10-18-spike-skeleton.md`; the reasoning worth keeping:

- *Images:* every photo goes through `app.images.prepare_image`: orientation applied, then the image is rebuilt from raw pixels (so EXIF/GPS/XMP/ICC cannot ride along), downscaled to a 1568 px long edge (configurable, `APP_IMAGE_MAX_EDGE`; image tokens scale with area, so this is also the cost lever), re-encoded as JPEG q85. Never upscaled. Tests and the mock spike use a generated image carrying fake GPS, so no real photo is needed anywhere.
- *Pricing:* one table, `src/app/pricing.py`, with source URL and date (checked 2026-10-18). Costs are always *estimates* from API-reported usage plus a configurable per-search estimate (`$0.01`, from "$10 per 1,000 searches"). Haiku 5.5's prompt-length tier is modeled; an unpriced model is costed at the highest known rate so the cap errs conservative and the table prints a warning.
- *Models:* defaults `claude-sonnet-5-5` (perception) and `claude-haiku-5-5` (retrieval), both confirmed on the models overview page. Config only; recorded per stage in trace and table.
- *Web search tool version:* default is the basic `web_search_20250305` (works on every model, results go straight into context) rather than the `_20260209`+ dynamic-filtering variants, because those run code execution under the hood and I could not verify Haiku 5.5 support or the token trade-off without a live call. `APP_WEB_SEARCH_TOOL` switches it so the two can be compared live.
- *Thinking effort:* `APP_EFFORT_PERCEPTION=medium`, `APP_EFFORT_RETRIEVAL=low` are guesses (thinking tokens bill as output). Explore live; they may be the biggest cost lever.
- *Perception schema (`schema_version` 1):* top-down plan in normalized coordinates (north = wall farthest from camera). Added a `furniture_gaps` list (categories the room visibly lacks) so retrieval slots have something to derive from. Living things are a separate list, never in `furniture`. Bounds (0..1 positions, confidence, positive sizes) are validated by pydantic *after* parsing; the JSON Schema sent to the API strips `maxItems`/`maxLength`/numeric bounds rather than pretending they work.
- *Slot derivation:* done in code, not by an LLM call, so the number of searching calls is bounded and inspectable. Order: furniture marked replaceable (`keepable: unlikely`), then gaps, then room-type defaults only if neither exists. Keepable items are never slots. Total budget is split equally across slots (spike heuristic). Slots run sequentially under one shared `Budget` (steps and dollars cap the whole run); parallelizing is a latency lever to test later (todo). [Superseded: slots run concurrently; slot order and the budget ceiling are now ADR 0007.]
- *URL guard:* a candidate is kept only if its URL appeared in that call's search results (ignoring only a `#fragment` and trailing slash). The mock deliberately returns one unverified URL per slot so the guard visibly fires in every mock run.

- `Config.max_cost_usd` (0.25) and `max_steps` (12) are still template guesses. They bound a whole spike run now; the proposed full-run target ($0.20) sits below the cap on purpose, but validate both against the exploratory run.
- **2026-10-23, size axes depend on the category.** An unlabeled `21"x79"` is width x height for tall
  products, width x length for flat ones, and longest side only for everything else, because guessing
  depth made a tall bookcase look like a 2 m deep footprint. A known height over ceiling minus 0.1 m
  now fails the fit check. All thresholds untuned. See ADR 0009 (amendment) and
  `docs/sessions/2026-10-23-size-parsing-fix.md`.
- **2026-10-23, run report is a static developer page.** Plain HTML and CSS written by the standard
  library (no jinja2 dependency, no script, a restrictive CSP), generated at the end of every run and
  from `make report(s)`. The floor plan is drawn only from perception positions; new picks with no old
  position are listed, never placed. See `docs/sessions/2026-10-23-run-report.md`.
- **2026-10-23, photo-real is the main goal (proposed, ADR 0011).** The owner decided the output is
  the visitor's own room photo with the picks in it, with the 2D plan as the instant first view. The
  family is reference-based placement (room photo plus product images plus real sizes), because
  restyle tools cannot keep or replace specific pieces and 3D/AR needs assets we lack. The spike is an
  experiment in its own package; no thresholds come from it. Vendor facts that could not be verified
  (OpenAI model id and price, Decor8 endpoints) block live runs until the owner supplies them.
- **2026-10-24, stage 2d: decide only what was read (ADR 0012 amended).** Live use showed titles-only
  fallback inventing preferences and a price band wider than the liked items. Decisions: shares count
  unknowns against every value with a 70% known-coverage floor; fallback learns only seller and price;
  a price band must hold 80% of the liked mass and of the liked items or price is mixed; the guard covers
  shape and open dimensions only, typed dimensions are exempt; every decision gets a visible trace. The
  80% rule on both mass and items was my choice where the brief said mass. See
  `docs/sessions/2026-10-24-shop-mode-stage-2d.md`.
- **2026-10-24, stage 2e: the model tags what was shown (ADR 0012 amended).** The title lexicon gave
  10% to 46% coverage of what the shopper saw, so the lift test almost never ran, and synonym splits cut
  real patterns below their thresholds. Decisions: one cheap call tags shown and candidate titles from fixed
  vocabularies (cached per result id); shape converges at 80%, soft dimensions at 60%; a seller chip needs
  40% of the like mass; the pool is searched for an open dimension's thin value instead of only reordering
  it; a metal frame with no colour named is `other`, not a colour. My choices where the brief was silent:
  candidate tags come back as text rows, not JSON objects (4x fewer tokens); "other" can never converge or
  be open; tagging failure means no attribute converges (open can still show); the rank model does the
  tagging. See `docs/sessions/2026-10-24-shop-mode-stage-2e.md`.
- **2026-10-24, stage 2f: retailers are a signal, dislikes net out, style is a family (ADR 0012
  amended).** The third session showed candidate tagging failing with no visible cause, a pool of the
  wrong retailers for someone who likes West Elm, a seller chip blocked by 1 dislike in 5, and one style
  split four ways. Decisions: log every tagging call and show its reason; a seller needs 3 times its
  dislikes in liked mass; a retailer table (owner-editable judgment) drives a tier chip and up to 3 peer
  searches per Shop Again, inside a 9-call cap; style is decided on two families. My choices where the
  brief was silent: marketplace and budget tiers never earn a chip or peer searches (a Lowe's table is about
  the table); a retailer-tier cap and the tier quota use the tier's like share; peers rotate and only a peer
  that found something is asked again; the mock serves a recorded pool for one replay through
  `APP_SHOP_MOCK_POOL`. See `docs/sessions/2026-10-24-shop-mode-stage-2f.md`.
- **2026-10-24, stage 2g: bound the cost, speed and duplicates of a Shop Again (ADR 0012 amended).** The
  fourth live session took 99 s: tagging calls failed 8 of 10 times and every failure retried in halves,
  all 265 candidates were tagged for 24 shown, and duplicates reached the grid. Decisions: a forced tool
  call in batches of 40 with one retry and no cascade; a tagging budget of 15 s, a target of 30 s and a hard
  stop at 45 s; the model tags only the top 60 by rank (keywords for the rest); searches and the preference
  call run concurrently; slow actions are background jobs the page polls; one de-duplication and one seller
  canonicalization everywhere. My choices where the brief was silent: the rank call runs BEFORE tagging, so
  supplied candidates are appended unranked; a job id is readable only with its session id and a new
  session's first search by id alone; one job per session and 8 in all; the tool schema is `strict` and a
  rejection falls back to the rows format on the one retry; a Shop Again gets its own step cap (40);
  replay 4 has 8 positive items (2 loved, 6 liked) and 38 dislikes, not 36, so the shape numbers are 67/33.
  See `docs/sessions/2026-10-24-shop-mode-stage-2g.md`.
- **2026-10-25, stage 2h: prepare while the shopper browses (ADR 0012 amended).** The live Shop Again took
  34.6 s and tagged what was shown from titles only. Decisions: tag every stored batch from title and photo in
  the background (cached with a source, a photo tag wins) and read each comment as it is written; the
  preferences call reuses them and is skipped when all is cached; a Shop Again waits at most 8 s for
  preparation, then falls back to the live path; preparation spend (cap $0.05 a session, 4 calls at once)
  is shown on its own in the footer; tagging starts as each search returns with one cap of 60 titles per
  Shop Again (this was 140 because the cap applied per step); a step bar replaces the spinner; one seller
  canonicalization feeds every table. My choices where the brief was silent: preparation is off in a bare
  `Config` and on from the environment; first-come tagging happens before the rank call, with a 12-title
  rank-ordered reserve; the fifth replay fixture was skipped (a saved session has no candidate pool). See
  `docs/sessions/2026-10-25-shop-speed-prep.md`.
- **2026-10-25, stage 2i: tailor from like rates (ADR 0012 amended).** The live Shop Again at 13.7 s learned
  nothing because "3 times the disliked mass" ignored hit rates. Decisions: one group like-rate function
  (rated, liked, rate against the all-ratings baseline) replaces the net-mass, share and lift rules for
  sellers and tiers; a leaning layer for soft values (toward at 4 rated, 2 liked, 1.5 times, 35%; away at 6
  rated and half the baseline) feeds the ranker and holds a 30% soft share or cap; the marketplace tier is
  excluded (chip, banner under 12, dismissal for 8 ratings) when 8 or more were rated at 20% or less; liked
  sellers are searched by name and the model writes validated queries; the base query stops at page 2 (page 3
  last resort). My choices where the brief was silent: up to 3 seller chips; a session where nearly
  everything was liked has no seller chip (nothing can be 1.5 times a baseline over 67%); leanings use title
  keywords for a dimension the tags left empty; query writing is off in a bare `Config` and on from the
  environment; the fifth replay fixture was not built (the newest session predates pool snapshots), a
  synthetic evidence fixture stands in. See `docs/sessions/2026-10-25-shop-tailoring.md`.
- **2026-10-25, stages 2j to 2m (ADR 0012 amended): topics, request understanding, refine, reviews and photos.**
  Decisions: a topic is the canonical category (owner's rule: reset on a different product, keep on a refinement,
  Saved always stays); the parse separates product words from setting words and suggests colours as soft guidance
  (never filters, 40% and 15% shares); refine chips outrank inferred chips and live in the topic; reviews are
  display only; More photos shares one cached lookup and the cap with Open. My choices where the brief was
  silent: a missing category resets with its own notice; deleting the setting chip also removes its colour
  suggestions; colour of rated items comes from cached photo or title tags (the preference prompt is
  unchanged); a refinement that cannot be read does not stop a Shop Again; a mock-only deterministic reader
  stands in for the three new model calls; the ranker's candidate line still shows ratings (as since stage 1).
  See `docs/sessions/2026-10-25-shop-batch.md`.
- **2026-10-25, stage 2n (ADR 0012 amended): fixes from the first live run.** Decisions: the gallery reads `thumbnails`
  then `media` (the documented field); near-duplicates use either of two signals (image hash, title) with price windows
  and keep one representative; a comment labelled as about the listing is never taste and its rating is excluded from
  every taste calculation but the item stays in seen memory; an unknown label from the reader is ignored. Mock-only
  switches `APP_SHOP_MOCK_DUPLICATES` and `APP_SHOP_MOCK_ONE_PHOTO` exist for the browser check. Existing tests edited:
  the prompt-version asserts (6 to 7) and the footer wording assert. See `docs/sessions/2026-10-25-shop-fixes.md`.
- **2026-10-26, stage 2o (ADR 0012 amended): gallery dormant, Open fixed, store links resolved ahead.** Decisions: the
  gallery stays in the code behind `APP_SHOP_GALLERY` because the lookup takes seconds and no faster source exists;
  Open opens its tab in the click with a loading message and falls back to Google's page (never a blank tab); loved
  and liked items are looked up in the background, 8 of the 12 lookups at most, 2 at a time. Existing tests edited:
  gallery tests now run with the flag on, two page-text asserts changed, and the lookup-trace assert gained the new
  keys. See `docs/sessions/2026-10-26-shop-open-fix.md`.
